# stark_planner

Generated by `new-service.mjs` — a LILAK Web Portal service on the kit's AppShell.

- **Frontend** (`frontend/`): React + Vite, aliases the kit via `LILAK_UI_PATH`.
  Shell = thin AppShell config in `src/components/Shell.jsx`; theme in
  `src/theme/main.js` (main colour `#2673c2`, blue-sky midpoint); tabs: sim, set.
- **Backend** (`backend/`): minimal FastAPI (health + whoami + serves `dist`).
  Runs on the shared portal venv; SSO via `portal_auth.py`.
- **Settings tab**: portal-centric — account + manage-users link to the portal; tabs/profile-types are service-local stubs.

## Run

    cd frontend && LILAK_UI_PATH=~/web_service/lilak_ui npm install && npm run build
    # backend (shared venv):  cd backend && uvicorn main:app --port 8170

## Register with the portal

A manifest was written to `data/stark_planner/service.json`. Register it via the portal
admin **Services** UI or `/api/handshake` (see service_manager). Fix `start.cwd`
per host if you move the checkout.

## What lives where

The `설계` tab is nptoy's simulation stage, cut down to the volume dock and
extended with the planner:

- `src/g4/Viewer.jsx`, `src/g4/styles.css` — copied verbatim from
  `nptoy/frontend/src/g4/`, so the 3D engine, style editor chrome, rail dock and
  volume tree behave exactly as they do there. The only local change is an
  optional `frame` prop: its own `fit()` takes the MEDIAN volume position as the
  world centre, which is robust for a dumped G4 tree of hundreds of similar
  volumes but jumps here — drag one ring past another and the median flips to a
  different ring, translating the scene out from under a camera that lives in
  world coordinates. `SimTab` pins the framing from a real bounding box
  (`sceneFrame`) and only re-reads it when you press `fit`.
- `src/pages/SimTab.jsx` — the stage: full-bleed `Viewer` + floating `RailNav`
  with the `planner` / `volumes` / `kinematics` / `profiles` / `z-edit` /
  `display` docks, an axis bar (±X/±Y/±Z) and `fit`.
- `src/pages/panels/ZEditPanel.jsx` — every component with a z on ONE shared
  scale, each with a numeric field and a drag bar. The coloured bar is the z
  range that component's body occupies and the thin line is the detector centre,
  so the rows read as a side elevation and a clash is visible, not just flagged.
- `src/pages/panels/VolumesPanel.jsx` — nptoy's volume tree, lifted as-is. It
  only knows the volume array, never STARK.
- `src/stark/` — the planner itself:
  - `data.js` ring + detector + material libraries, transcribed from the
    "STARK detectors/rings" sheet (tabs `I_Rings`, `I_Detectors`)
  - `physics.js` relativistic two-body kinematics, beam optics, Bethe-Bloch,
    the sheet's silicon dE tables (`eloss_si.js`, lazy-loaded)
  - `geometry.js` placed detector faces, theta/solid angle, coverage, collisions
  - `scene.js` **the bridge**: a setup -> the nptoy volume array the Viewer draws
  - `model.js` everything derived from a setup; `store.jsx` holds the setup
  - `nuclides.js` NUBASE2016 mass excesses (atomic — `PH.nuc` strips the electrons)

## Profiles

A profile is one whole setup (beam / collimator / target slots, rings, single
detectors, reaction), stored on the backend under
`~/web_service/data/stark_planner/profiles/<account>/<id>.json` — one folder per
portal account, so a profile follows you across browsers and machines. The
`profiles` dock saves over the open one, makes a **copy** (of what is on screen
for the open profile, of the stored body for any other), starts a **new** one
from the stock STARK 0330 layout, and can publish one read-only to the rest of
the portal (`공유`). The working setup also autosaves to `localStorage`, so a
reload never loses it even with the backend down — only the named profiles need
the API.

`backend/profile_seed/*.json` ships built-in profiles with the service (owner
`_seed`). They appear for every account, load and copy like any other, and
cannot be edited or deleted — so the stock STARK 0330 layout is always one click
away no matter what anyone does to their own list. Regenerate one with:

```bash
node --input-type=module -e "import {defaultSetup} from './frontend/src/stark/data.js'; console.log(JSON.stringify(defaultSetup(),null,2))"
```

Backend: `profiles.py`, a drop-in router in the same style as `layout.py`.

## Ring mounts

`mount: 'frame'` (default) hangs the wafers on a ring body: `z` is the frame's
front face, `off` carries it to the detector centre, and the body claims a
z/radius volume no other framed ring may enter. `mount: 'bare'` drops the frame
— `z` IS the detector centre, nothing is drawn for the mount, and the ring is
skipped by the collision check. Use it to sketch a layout before there is a
mechanical design to hang it on.

## Telescope pairs

Two rings can be bound as a dE-E pair (`pair` on each, symmetric). Their edge
angles can only line up exactly when `h/r` agrees, which it does not for X6 at
r 109.2 against BB10 at r 91.7 — so **각도 맞추기** solves for the z that minimises
the two edge mismatches (`GEO.matchZ`) and reports the residual instead of
pretending it is zero. For the stock 12E/12dE pair that is 3.95° → 1.97°.

## Check

```bash
node src/stark/selfcheck.mjs
```

Q values, the sheet's phi/theta to six decimals, collimator transmission against
the analytic result, Bethe-Bloch against PSTAR, flip mirroring, and that stacked
dE-E layers do not double-count solid angle.

## Dev

```bash
cd frontend && LILAK_UI_PATH=~/web_service/lilak_ui npm run dev   # :5170
~/web_service/service_manager/.venv/bin/python -m uvicorn main:app --port 8170  # from backend/
```

Vite proxies `/api` to `:8170`. Without the backend the planner still works;
only the profiles dock reports itself offline.

The manifest `data/stark_planner/service.json` is written but **not registered**
with the portal — add it from the admin Services UI or `/api/handshake`.
